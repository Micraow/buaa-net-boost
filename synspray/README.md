# synspray：同 5 元组复读 SYN

验证校园网 IPv6 的“新流首包丢失”是不是严格的“只丢第一个包”。实测表明不是：同一 5 元组的前 K 个包会被连续丢弃/限速，K 随流和时段变化；把内核的 SYN 原样复读 K 次，第 K 份穿过后握手立即完成，不必等内核 1 秒的 RTO。

## 原理

1. 内核 socket 正常 `connect()`，发出第一个 SYN；
2. 用 `AF_PACKET` 抓下这个 SYN（相同源端口、ISN、TCP 时间戳、选项）；
3. 重算 TCP 校验和（抓包可能是 checksum offload 的半成品）；
4. 用 raw IPv6 在同一 5 元组上按间隔复读同一份字节；
5. 每发一份就 poll 一次，内核 socket 收到任何一个 SYN-ACK 就完成握手并立即停止复读。

复读包与内核 SYN 完全一致，服务端会把它当作 SYN 重传，不会建立多条连接。

## 构建与运行（需要 root）

```bash
cd synspray
gcc -O2 -Wall -o synspray synspray.c
sudo ./test.sh 2402:f000:1:400::2 443 25 8 20 3000
# 更稳的 16 份：
sudo ./test.sh 2402:f000:1:400::2 443 25 16 20 3000
```

参数：目标 v6、端口、试验次数、复读份数、间隔 ms、超时 ms。`test.sh` 先跑同样次数的普通 connect 作为基线，再用 sudo 跑复读。

## 实测结果（2026-11-02）

### TCP：TUNA `2402:f000:1:400::2:443`，`wlan0`，50 次/组，3s 超时

| 方式 | 成功 | 成功者中位 | 备注 |
|---|---|---|---|
| 普通 connect | 17–18/25 | 1021–1023ms | 两次 25 次基线；首包丢失后靠内核 1s/2s 重传 |
| 单路径 8 份 / 20ms | 46/50 | 68ms | 4 次 3s 超时 |
| 单路径 16 份 / 20ms | 49/50 | 47ms | 1 次 3s 超时 |
| 双路径 8+8 / 20ms | 50/50 | 26ms | 47/50 两条都通；取最先成功的一条，最慢 130ms |

8 份那 4 条失败流，隔 2 秒用**同一个源端口**重试，4/4 成功（1–6 份就通）；16 份那 1 条也在 9.7ms 内通了。因此没有观察到永久按流黑洞，失败是超过 140/300ms 的**瞬时窗口**。

### UDP：Cloudflare DNS `2606:4700:4700::1111:53`，`wlan0`，50 次/组

| 方式 | 成功 | 成功者中位 | 备注 |
|---|---|---|---|
| 单包 | 15/50 | 43ms | 70% 首包丢失 |
| 同 5 元组 8 份 / 20ms | 45/50 | 81ms | 第一份响应常在第 3–8 份 |
| 同 5 元组 16 份 / 20ms | 50/50 | 75ms | 最慢 347ms |
| 双路径 8+8 / 20ms | 44/50 | 65ms | 不如单路径 16 份；UDP 要加深，不要加宽 |

UDP 的 8 份失败 5 条，16 份 0 条。DNS 查询可重复（同 ID），QUIC Initial 也可重复；任意 UDP 要先确认重复语义。

### 一批探测的推荐参数

- TCP：**2 条路径 × 8 份，20ms，一轮**；第一条 SYN-ACK 胜出，另一条 RST 关闭；1s 超时；全失败再重试一轮或回退 IPv4。
- UDP：**1 条路径 × 16 份，20ms，一轮**；第一份响应胜出；重复响应去重；300ms 无响应再换 5 元组或回退（DNS 可改走 TCP/DoH）。

这里的“双路径”是**两个不同源端口/5 元组**，不是两个物理出口；当前只有 `wlan0` 有全局 IPv6。

## 换网络/时段复测时怎么看

| 现象 | 含义 |
|---|---|
| 复读成功率和普通接近，延迟也接近（1–2s） | 设备按会话/状态丢，复读没用；用多源端口或隧道 |
| 复读成功率明显更高，延迟降到几十毫秒 | 前 K 包连续丢失；这个思路有效，值得做成透明层 |
| 复读成功率反而低 | 复读包被识别为异常/重复，触发限速；放弃 |

## 实现注意

- `IPPROTO_RAW` 发送完整 IPv6 包时，`sockaddr_in6.sin6_port` 必须为 0（端口在 TCP 头里）；非零端口会被本机内核以 `EINVAL` 拒绝，这是最初 `sendto: Invalid argument` 的原因。
- TCP socket 和 raw socket 都用 `SO_BINDTODEVICE` 绑定到抓包接口，避免 TUN/多网卡下与基线走不同路径。
- 本地端口传 0，由内核分配；bind 后用 `getsockname` 读回实际端口，抓包过滤才不会错。
- 必须每发一份就 poll；如果发完所有份才 poll，“成功时间”会被误报成最后一份的发送时间。
- 已在用户命名空间的 loopback 上做端到端验证：`sent` 等于实际份数、`ok=1`，监听端成功 `accept`；真实链路需要 root 运行。

## 注意

- 需要 root：`AF_PACKET` 抓包 + `SOCK_RAW` 发送。
- 假设链路层是 14 字节以太网头、无 VLAN；当前 `wlan0` 满足。
- 服务端可能对重复 SYN/重复 UDP 做速率限制；只在自己/授权网络测试。
- UDP 复读只对可重复的协议安全（DNS 同 ID、QUIC Initial）；任意 UDP 可能重复触发副作用，需协议识别或改用隧道。
- 这个工具只验证 `connect()`，不承载数据。透明化/代理化的实现方式：
  1. SOCKS5/HTTP CONNECT 代理 + 特权小助手：应用把代理指向本地，helper 负责抓包和复读；浏览器、Telegram 等可直接用。
  2. eBPF `cgroup/connect6` + 本地复读代理：按 cgroup 透明重定向，和 IPv4 的 `connect4` 思路相同，需要 cgroup v2 和 root。
  3. TUN + 用户态 TCP/IP 栈：覆盖所有应用，但实现最重，适合做成 Android 本地 VPN。
  4. 远端 IPv6 长连接隧道：建一条长连接后复用，避开每条新流的 SYN 丢失；适合 UDP/QUIC 和不能设代理的应用，但需要远端端点。
