# TCP 多源端口握手竞速（验证原型）

针对“出口按 5 元组哈希选路、8 桶中 4 桶黑洞、同一 5 元组重试无效”的问题，做一个只冗余握手、不冗余应用数据的客户端规避。

## 原理

1. 对同一目标、同一目的端口，用 N 个不同源端口**并行**发 SYN；
2. 第一个完成三次握手的连接胜出，其余立即 RST 关闭；
3. 应用数据只在胜出的那条连接上发送；
4. 连接后续失效，再重新做一轮竞速。

因为观测到的位图是 8 周期、坏桶最长连续 4 个（`11100001` 中的 `0000`），**5 个连续源端口必然至少有一个落在好桶**。

## 概率

独立模型（p=0.5）：`P = 1 - 0.5^N`

| N | 独立概率 | 周期 8 下的实际保证 |
|---|---|---|
| 1 | 50% | 50% |
| 2 | 75% | 取决于起点 |
| 3 | 87.5% | 取决于起点 |
| 4 | 93.75% | 可能落在连续 4 个坏桶 |
| **5** | 96.9% | **必然至少 1 个好** |
| 6 | 98.4% | 必然 |
| 8 | 99.6% | 必然 |

实际位图有 5%–20% 的缺陷位，建议 N=6–8。

| N=4，坏桶起点 | 0/12 |


## 用法

### 握手竞速基准

```bash
../userspace/bin/probe --n <N> --trials <trials> --base <base> <ip> <port>
# 例：
../userspace/bin/probe --n 5 --trials 12 --base 20003 223.5.5.5 443
```

### 竞速代理（HTTP CONNECT + SOCKS5 CONNECT）

```bash
../userspace/bin/tcp-race --listen 18080 --n 5 --rounds 2 --base 20000 --step 8

# HTTP CONNECT
curl -x http://127.0.0.1:18080 -k https://104.16.132.229/

# SOCKS5（域名交给代理解析）
curl --socks5-hostname 127.0.0.1:18080 -k \
  https://mirrors.tuna.tsinghua.edu.cn/ubuntu/ls-lR.gz -r 0-1000000 -o part.bin
```

代理特性：

- 每个新连接在 `[base, end)` 内取一个 N 端口窗口，窗口按 `step=8` 滚动，避免复用同一 5 元组；
- 竞速失败时自动换下一个窗口重试（`--rounds`）；
- 已连接的败者用 RST 关闭；胜者在隧道结束后正常关闭；
- 隧道空闲 600 s 自动断开；
- 竞速是并行的，首个成功仍在约 1 个 RTT。

实测：HTTP CONNECT 10/10；SOCKS5 经域名下载 1 MB 返回 `206`、`size=1000001`。

代理内的 `resolve()` 用 UDP DNS（`223.5.5.5`，绑定 wlan0）解析域名；换环境时按需修改。若需要 IPv6，需另加 `AF_INET6` 分支。

## 注意事项

- **必须滚动端口窗口**：固定 base 时，胜者端口正常关闭后会进入 TIME_WAIT/NAT 残留，下一次复用同一 5 元组会失败；实测表现为“成功一次、失败一次”交替。滚动窗口 + RST 关闭后 8/8 稳定。
- **N=5 是理论最小**，依赖“坏桶最长连续 4 个”这一观测；实际建议 6–8。
- **只对 TCP 有效**。QUIC/UDP 需要另做（多源端口发 UDP 探测、选可用的那条，但 QUIC 的连接迁移更复杂）。
- 每个新连接会多产生 N−1 个 SYN；对端或校园侧可能视为扫描或触发 SYN 限速，N 不要太大。
- 连接建立后若路径失效，竞速不会自动迁移；需要应用层检测到中断后重新竞速/重连。
- 源端口要避开系统临时端口范围；如果途中有 NAT 改写源端口，桶选择不再可控，但随机源端口竞速仍能提高成功率。
- 仅在自有/授权环境使用，不要用于绕过计费或对第三方发起探测。
