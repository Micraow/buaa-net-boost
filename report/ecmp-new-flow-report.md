# 校园网 IPv4 新建连接按流哈希失效的观测报告

- 观测时间：2026-11-01 深夜
- 测试主机：Linux，无线网卡 `wlan0`，IPv4 `<CLIENT_V4>/16`，网关 `<GATEWAY_V4>`
- 所有探测绑定 `wlan0`、使用数字 IP；DNS 相关的陷阱见 3.6

---

> 说明：`<CLIENT_V4>`、`<GATEWAY_V4>`、`<NAT_CT>` 等为脱敏占位符，复现时替换为实际地址。

## 0. 结论摘要

1. 外部目标的新建 TCP 连接约 40%–60% 失败，表现为静默超时；校内目标、已建立连接、部分目的地完全正常。
2. 失败**按 5 元组粘住**：同一源端口连续 3 次要么全成功、要么全失败（10/10），换源端口才可能改变结果。
3. 按源端口扫描得到**周期为 8 的确定性位图**，4 个桶好、4 个桶坏；lag8 是唯一显著周期。
4. 不同目的地分组对应不同的“好坏桶”分布：阿里/百度/Cloudflare 一组，GitHub/清华是它的**精确补集**，Apple/Microsoft/网易全通。
5. 全通组与走哪条上联直接相关：Apple/Microsoft/网易走**中国联通**，全通；Cloudflare/阿里/百度走**中国电信**，约一半桶坏；清华走 **CERNET**，坏桶与电信组互补。
6. 这不是随机丢包、带宽不足或服务端问题，而是**出口侧按流哈希在多条路径/成员中选择，其中约一半成员失效**。属于 ECMP/LAG 成员健康问题。

---

## 1. 现象

- 浏览器、命令行访问外部站点时，新建连接经常卡住数秒后超时；已有连接不受影响。
- 同一目标有时毫秒级成功，有时完全无响应；重试同一连接无效，换一个连接（新源端口）可能立刻成功。
- 校内服务、校内任何可达的本地设备始终正常。
- 关闭端口也收不到 RST（不是服务端拒绝，是包被静默丢弃）。

---

## 2. 方法

| 项目 | 做法 |
|---|---|
| 出口绑定 | `SO_BINDTODEVICE=wlan0`，绕开本机路由策略，确保走物理出口 |
| 固定源端口 | `bind(("", port))` + `SO_REUSEADDR` + `SO_LINGER(1,0)`（RST 关闭，避免 TIME_WAIT 干扰） |
| 建连判定 | `connect()` 在 0.8–1.5 s 内返回为成功，超时为失败 |
| 周期性 | 对位图做 lag 2–16 的自相关，相同值比例最高的 lag 即周期 |
| UDP 对照 | 绑定源端口后发送 NTP 请求，1 s 内收到回复为成功 |
| NAT 出口 | 向 STUN 服务器发 Binding 请求，解析 XOR-MAPPED-ADDRESS |

### 3.6 测量陷阱：本地接管的 DNS

明文 DNS 会被本地接管，制造“UDP 一直正常”的假象：

- 所有明文 UDP 53（包括直接发往 `8.8.8.8`）查询 `github.com` 都返回 `205.164.50.200/202/208`；
- 改用 TCP 53 查询同一解析器，返回真实地址 `20.205.243.166`；
- `o-o.myaddr.l.google.com`：UDP 53 返回 `<CAMPUS_EGRESS>`（校内），TCP 53 返回 `172.253.6.27`。

因此：**UDP DNS 的 100% 成功不是出口路径的证据**，是本地解析器应答。真实外部 UDP 新流（NTP）成功率只有 30%–53%。

## 4. 分析与推理

### 4.1 可以排除的解释

| 假设 | 反证 |
|---|---|
| 带宽不足 | 已建立连接仍可传输（成功样本 2.55 MB/s），失败只发生在新流建立阶段 |
| 逐包随机丢包 | 同一 5 元组连续重试结果完全一致；换源端口才改变 |
| 服务端限流 | 同组不同目标表现一致；同目标换源端口即可成功；校内目标 100% |
| 本地协议栈/配置 | 校内目标 10/10；同一终端、同一绑定方式，只有特定目的地分组失败 |
| DNS 解析问题 | 全部使用数字 IP 测试，未经过解析 |
| 端口策略 | 目的端口 443/80 位图相同；关闭端口同样收不到 RST |

### 4.2 最符合的模型

- 出口存在一个**确定性的按流哈希**，把新流分配到有限的桶里；
- 桶对应多条路径/成员，其中约一半当前不可用；
- 哈希键包含源端口、协议、目的网络（下一跳组），不包含目的端口和同组内的目的 IP；
- 选中可用成员的流毫秒级成功；选中失效成员的流被静默黑洞，且同一 5 元组重试仍走同一成员；
- 不同下一跳组的成员顺序或路径集合不同，所以电信组与 CERNET 组的好/坏桶互补，联通组全通。
- 全通组（Apple/Microsoft/网易）实际都走联通；失败组（Cloudflare/阿里/百度）走电信；清华走 CERNET。失败与"走哪条上联"直接相关。

### 4.3 关于“8”

可观测到 8 个桶、4 好 4 坏。两种拓扑都能解释：

1. 2 条并行路径/平面，1 位选择，其中一条完全不通；
2. 8 个 ECMP/LAG 成员，其中 4 个失效。

仅凭终端位图无法区分这两种；两者都属于出口侧 ECMP/LAG 成员健康问题。

---

## 5. 影响与临时规避

- 受影响的流：新建连接；同一 5 元组重试无效。
- 不受影响的流：已建立连接、校内目标、被本地接管的 DNS、当前走健康上联的目的地（Apple/Microsoft/网易等）。
- 终端侧唯一有效的规避是**换新连接（新源端口）**，而不是在同一连接上等待；长连接复用可显著减少受影响面。
- 根因在出口设备，终端无法修复。

---

## 6. 建议的网络侧检查

1. **优先检查中国电信（AS4134）和 CERNET 两条上联**的 ECMP/LAG 成员状态：成员数、每个成员的 up/down、实际哈希桶分布。联通（AS4837/AS4808）当前全通，可作为健康基线。
2. 检查 **BFD / 链路聚合**：是否存在成员单向不通或反复 flapping。
3. 检查**核心双平面 / 双 BRAS**：是否一台失效，而部分业务仍按 50/50 分发。
4. 检查 NAT 出口池（`<NAT_CT>`、`<NAT_CU>`）对应网关的会话表与健康状态。
5. 在出口抓包，确认哈希到失效成员的 SYN 是否离开校园。

复现方法：对任一受影响目标，绑定不同源端口各建连一次，画出 1/0 位图；若出现 8 周期、4 好 4 坏，即可复现。

---

## 7. 局限

- 仅终端侧观测，无法看到具体是哪台设备、哪个成员丢弃了包。
- 未抓包，无法区分“请求没出去”与“响应没回来”。
- 桶数“8”是从周期推断的，不能直接证明设备配置为 8 个成员。
- 位图有 5%–20% 的缺陷位；较长尺度上会翻转，说明成员状态或哈希映射不是完全静态的。

## 8. 命令与输出

### 8.1 单次建连（绑定源端口、绑 wlan0）

```python
import socket, struct
def att(ip, port, lport, to=0.9):
    s = socket.socket()
    s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.setsockopt(socket.SOL_SOCKET, 25, b"wlan0")          # SO_BINDTODEVICE
    s.setsockopt(socket.SOL_SOCKET, socket.SO_LINGER, struct.pack("ii", 1, 0))
    s.bind(("", lport))
    s.settimeout(to)
    try:
        s.connect((ip, port)); r = 1
    except Exception:
        r = 0
    s.close()
    return r
print(att("223.5.5.5", 443, 45000))
```

## 9. 客户端规避验证：多源端口握手竞速

**原理**：对同一目标、同一目的端口，用 N 个不同源端口并行发 SYN；第一个完成握手的连接胜出，其余立即 RST 关闭；应用数据只走胜出的连接；连接失效后再重新竞速。

**为什么是 5**：观测到位图为 8 周期、坏桶最长连续 4 个（`11100001` 中的 `0000`），所以 5 个连续源端口必然至少有一个落在好桶。

| N | 独立概率（p=0.5） | 周期 8 下的保证 |
|---|---|---|
| 1 | 50% | 50% |
| 4 | 93.75% | 可能正好落在 4 个连续坏桶 |
| **5** | 96.9% | **必然至少 1 个好** |
| 6–8 | 98.4%–99.6% | 必然（建议值，覆盖缺陷位） |

**实测**（坏桶起点 55003，该段坏桶为 55003–55006）：

| 配置 | 结果 |
|---|---|
| N=1，坏桶起点 | 0/12 |
| N=4，坏桶起点 | 0/12 |
| N=5，坏桶起点 | 12/12，胜者始终 55007 |
| N=6 / N=8 | 12/12 |
| N=1，好桶起点 55000 | 12/12 |

**端到端**（HTTP CONNECT 代理，目标 Cloudflare，10 次）：

| 配置 | 成功 |
|---|---|
| N=1，坏桶起点 | 0/8 |
| N=4，坏桶起点 | 0/8 |
| N=1，好桶起点 | 8/8 |
| N=5，滚动端口窗口 | 8/8 |

真实数据（经代理下载清华 TUNA 1 MB）：

```
http=206 size=1000001 time=1.26s
实际文件大小: 1000001
```

**关键实现细节**：

- 必须**滚动端口窗口**（每次连接把起点后移 8 个端口）。固定起点时，胜者端口正常关闭后会进入 TIME_WAIT/NAT 残留，下一次复用同一 5 元组会失败，实测表现为“成功一次、失败一次”交替；
- 胜者和败者都用 `SO_LINGER(1,0)` RST 关闭；
- 竞速是并行的，首个成功仍在约 1 个 RTT，不增加正常延迟；
- 只冗余握手，不重复应用数据。

**局限**：

- 只对 TCP 有效；QUIC/UDP 需要另做；
- 每个新连接多产生 N−1 个 SYN，N 过大会触发对端/校园的 SYN 限速或扫描告警；
- 连接建立后路径失效不会自动迁移，需要应用层检测并重新竞速；
- 若途中有 NAT 改写源端口，桶选择不再可控，但随机源端口竞速仍能提高成功率。

**改进后的 TCP 代理**：支持 HTTP CONNECT + SOCKS5、端口窗口滚动、多轮重试、空闲回收；实测 HTTP CONNECT 10/10，SOCKS5 经域名下载 1 MB 返回 `206`、`size=1000001`、`0.70s`。

### 9.1 UDP 竞速

对每个新的客户端 UDP 流，用 N 个连续源端口同时发送首个数据报；第一个收到目标回复的 socket 胜出；后续数据报只走胜者。

实测（NTP `203.107.6.88:123`，每请求一个新流）：

| 配置 | 成功 |
|---|---|
| N=1 | 14/20 |
| N=4 | 14/20 |
| **N=5** | **20/20** |
| N=5，复用同一流 | 20/20 |

UDP 的坏桶相位在几分钟内有漂移，N=4 不足以稳定覆盖；N=5 稳定 100%。只对“有回复”的 UDP 协议可靠；单向流量无法判定胜者。

### 9.2 eBPF 还是 TUN

- 竞速本身必须在用户态；eBPF/TUN 只负责把流量透明地送到竞速器，不能替应用在多个候选连接中选一个。
- 系统级首选：**eBPF `cgroup/connect4` 改写目标到本地代理**，开销低、无 TUN 设备；
- 没有 eBPF 时：nftables REDIRECT 到本地代理；
- TUN 是兜底：UDP 自然，但 TCP 需要用户态栈或再转给代理，开销和复杂度最高；
- 单应用 TCP：LD_PRELOAD 拦截 `connect()` 最简单。

详细对比见 [tcp-race/ebpf-vs-tun.md](../docs/ebpf-vs-tun.md)。

原型与用法见 [tcp-race/README.md](../docs/tcp-race.md)（`proxy.py`、`probe.py`）和 [udp-race/README.md](../docs/udp-race.md)（`udp_race.py`）。

### 9.3 eBPF 实装

结构：`cgroup/connect4` 只负责把目标 `IP:port` 的 connect 改写到 `127.0.0.1:18080`；竞速在用户态代理里完成。

| 文件 | 作用 |
|---|---|
| `tcp-race/ebpf/connect_redirect.bpf.c` | cgroup/connect4 程序，匹配目标后改写并 `bpf_printk` |
| `tcp-race/ebpf/loader.c` | 加载 BPF、写 map、挂 cgroup |
| `tcp-race/ebpf/run_test.sh` | 建 cgroup、起代理、挂 BPF、跑 curl、收集日志 |

关键设计：**代理和 loader 放在 root cgroup，只把测试客户端放进被挂载的 cgroup**，否则代理自己到目标的 connect 会被重定向成环。

无 root 部分已验证：透明代理 + TLS 客户端（模拟重定向后的目标）三次均返回 `HTTP/1.1 301`，日志为：

```
[syn] window 20000-20004 (5 sockets)
[syn] port 20004 SYN-ACK at 194ms
[syn] port 20000 no reply, closing at 2500ms
[syn] port 20001 no reply, closing at 2500ms
[syn] port 20002 no reply, closing at 2500ms
[syn] port 20003 no reply, closing at 2500ms
[transparent] OK -> 104.16.132.229:443 winner=20004 round=1 t=195ms
```

三次的胜者分别是 20004、20010、20017，均在 160–195 ms 完成，其余四个端口无回音。这就是“多 SYN 猜测”的完整过程。

eBPF 加载需要 root；加载后 `trace_pipe` 会额外输出：

```
race redirect 104.16.132.229:443 -> 127.0.0.1:18080
```

实机加载（2026-11-02）：直连对照组 1–4/5，经 eBPF 竞速 5/5、3/3；`connect=0.0001s` 证明重定向生效；竞速胜者 160–190 ms，健康目标 Apple 首端口 4–6 ms 即胜出；Cloudflare 直连成功约 0.55 s，经代理约 0.59–0.80 s。

与 TUN / fake-ip 的关系：connect 钩子在 TUN 之前运行，代理上游绑 wlan0，两者可共存；但 fake-ip 下钩子看到 198.18.x 假地址，匹配不到真实目标，需要 redir-host 或应用层代理；只把客户端应用放进被挂载的 cgroup，避免把 mihomo/代理自己重定向成环。
